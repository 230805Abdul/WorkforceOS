# Security Notes

This document is written the way you'd explain your security decisions in an interview — what's
implemented, why, and what's deliberately left as a documented gap rather than silently skipped.

## Authentication & authorization

- **Passwords**: hashed with bcrypt (via passlib), never stored or logged in plaintext. Minimum length
  enforced at the schema level (`UserCreate.password: Field(min_length=8)`).
- **JWTs**: short-lived access tokens (30 min default) + longer-lived refresh tokens (7 days), signed with
  HS256. The access token carries the user's role so RBAC checks don't need a DB round-trip on every request.
- **RBAC**: enforced via a FastAPI dependency (`require_roles(...)`) at the route level — explicit allow-list
  per endpoint, not a global policy engine that's easy to misconfigure.
- **Login response doesn't distinguish** "no such user" from "wrong password" — both return a generic 401, so
  the endpoint can't be used to enumerate registered emails.

## Transport & headers

- `SecurityHeadersMiddleware` sets `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Permissions-Policy`, and HSTS on every response.
- TLS termination happens at the ALB (`terraform/ecs.tf`), with `ELBSecurityPolicy-TLS13-1-2-2021-06` —
  TLS 1.2 minimum, modern cipher suites only.
- CORS is restricted to an explicit origin allow-list (`CORS_ORIGINS` in config), not `*`.

## Rate limiting

- `/auth/login` and `/auth/register` have tighter per-IP limits (10/min and 5/min respectively) than the
  rest of the API (60/min default), specifically to slow down credential stuffing and account-creation abuse.
- Known limitation: this uses in-memory storage (slowapi's default), which doesn't share state across
  multiple API tasks. For real multi-instance deployments, back it with the same Redis instance already in
  the stack — noted here rather than silently shipped as "handled."

## Data protection

- RDS and ElastiCache both have `storage_encrypted` / `at_rest_encryption_enabled` set, and the S3 resume
  bucket uses SSE-AES256 plus versioning (protects against accidental overwrite/delete, not just unauthorized
  access).
- Nothing touching the database or cache is reachable from the public internet — see the security group
  definitions in `terraform/security_groups.tf`. Only the ALB has an internet-facing ingress rule.
- The app's `SECRET_KEY` is generated by Terraform (`random_password`) and stored in AWS Secrets Manager,
  injected into the ECS task via `secrets`, never baked into the image or committed to the repo.

## Secrets & least privilege

- The ECS task role (what the *application* can do at runtime) is scoped to exactly one S3 bucket's objects —
  not `s3:*` on `*`. The execution role (what *ECS itself* can do, e.g. pull images) is kept separate from the
  task role, so a compromised container can't use the execution role's permissions.
- CI/CD authenticates to AWS via GitHub's OIDC provider (`terraform/iam.tf`), not a long-lived IAM access key
  stored as a repo secret — the trust policy is scoped to one specific repo/branch.

## What a real pentest pass would add

This scaffold covers the baseline OWASP-scanner findings (headers, auth, encryption at rest/in transit,
network segmentation). A genuine security project write-up — which is what gets you hired for security-adjacent
roles — should go further:

1. Run `OWASP ZAP` or `Trivy`/`Snyk` against this codebase and the built container image, then document and
   fix what comes back. (This is deliberately left as your next step, not pre-solved here — doing it yourself
   and writing up the findings is the actual portfolio artifact.)
2. Add structured audit-log alerting (e.g. N failed logins from one IP in 5 minutes → alert).
3. Rotate the JWT signing key with a key-ID (`kid`) claim and a short grace period, instead of one static key.
4. Add request body size limits and stricter input validation fuzzing on every POST/PATCH endpoint.
